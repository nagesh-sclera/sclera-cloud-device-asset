02

What is Dapr?

Dapr

The short version

Dapr is a middleman process that sits next to your service and handles the hard networking problems so your code doesn't have to.


Think of it like a post office clerk sitting at your desk — you hand them a letter, they figure out the routing, retries, and delivery. You write business logic, not network plumbing.

The four building blocks Sclera uses

1
Service Invocation (sync)
You call invoke/vdms-service/method/vdms/id — Dapr finds where that service actually is, with retries.
2
Pub/Sub Messaging (async)
Publish an event to a topic name. Dapr writes it to Redis and routes it to all subscribers. No direct connection needed.
3
State Store
Key/value over Redis — used here for the VDMS read-through cache (5 min TTL) and subscriber idempotency keys (24 h TTL).
4
Jobs (scheduler only)
The Dapr Jobs API + a standalone Scheduler control plane fire cron jobs exactly-once cluster-wide.

The Sidecar Pattern

Each service gets its own Dapr process. They share the same network namespace — meaning they reach each other on localhost.

Your App
☕
Spring Boot
Writes business logic. Calls localhost:3500 to use Dapr features.
Dapr Sidecar
📮
daprd
Handles service discovery, pub/sub, state, retries, and observability.
Both share the same Docker network namespace — they see each other on localhost

The two Dapr APIs you'll see most

// 1. Synchronous call to another service GET localhost:3500/v1.0/invoke/{app-id}/method/{path} // 2. Publish an async event POST localhost:3500/v1.0/publish/{pubsub}/{topic}
Your app always talks to localhost:3500. Dapr handles everything else — no IP addresses, no service URLs, no load-balancer config in code.

API Gateway — The Front Door

Architecture

What it does

The API Gateway (Spring Cloud Gateway, reactive WebFlux) is the only container that accepts traffic from the browser. It is a reverse proxy — it strips or passes URL prefixes and forwards to the right backend. It does not do authentication or business logic; JWT validation happens inside device-asset.

Example: GET /asset/api/v1/devices
Gateway strips /asset → forwards GET /api/v1/devices to sclera-cloud-device-asset:8085.
Every route strips its prefix (StripPrefix=1) except /vdms/**, which is proxied as-is.

Device-Asset — The Core Service

Architecture

What it manages

The heart of the application — every device, building, floor, sensor, document, and AI suggestion lives here, with all CRUD operations. Spring Boot 4.0.6 / Java 21 / PostgreSQL.

Package structure

PackageResponsibility

How it talks to VDMS Service (sync)

// VdmsClient.java (device-asset side) public Map getVdmsDetails() { // calls localhost:3500 (its own Dapr sidecar) return invoke("vdms/details", Map.class); } private T invoke(String path, Class<T> type) { String url = daprBase + "/v1.0/invoke/vdms-service/method/" + path; return rest.getForEntity(url, type).getBody(); }

How it publishes async events

// UserActionLogService triggers this via dapr-commons publisher.publish("device.audit", payload); // under the hood: POST localhost:3500/v1.0/publish/pubsub/device.audit // Dapr writes to Redis → delivered to subscribers
Publishing is fire-and-forget. The service returns immediately; Dapr + Redis guarantee at-least-once delivery even if the subscriber is momentarily down.

VDMS Service & the dapr-commons Library

Architecture

VDMS Service — what it stores

VDMS = Virtual Device Management System. A dedicated store (Postgres vdms_svc schema) for VDMS identity/config — property address, customer org ID, master-unit flag — and device audit logs.

Controllers

ClassRole
VdmsControllerServes VDMS identity data; registers Dapr subscriptions via GET /dapr/subscribe
VdmsSubscriberReceives CloudEvents from device-asset; updates VDMS rows on property/org changes
AuditSubscriberReceives device.audit events → persists to user_action_log; exposes GET /vdms/audit-log (paginated)

dapr-commons — the shared library

A single library that standardizes pub/sub across all 12 services so nobody re-implements the plumbing.

TypeRole
DaprEventPublisherPublishes with auto event IDs + structured errors
DaprEventSubscriber<T>Idempotency via state store; permanent-vs-transient error split; auto dead-letter routing
Event objectsDeviceAuditEvent, SchedulerTriggerEvent, SchedulerResultEvent, Vdms*Event, …

Idempotency & dead-letter (why it matters)

Exactly-once effect: each subscriber records processed event IDs in the statestore-idempotency Redis store (24 h TTL). A redelivered event is recognized and skipped.
Poison messages: unrecoverable events are routed to a *.dlq dead-letter topic instead of being retried forever.

What a CloudEvent looks like

Dapr wraps your payload in a CloudEvent envelope before delivering it to the subscriber.

{ "specversion": "1.0", "source": "sclera-cloud-device-asset", "topic": "device.audit", "pubsubname": "pubsub", "id": "a1b2…", // used for idempotency "data": { "vdmsId": "VDMS760", "action": "ADD", "deviceId": "dev-123", "userEmail": "admin@sclera.com" } }
The subscriber reads the data field; dapr-commons handles the envelope and dedupes on id.

The Scheduler — A Control Plane, Not a Worker

End-to-End Flow

The idea

sclera-scheduler fires events; it never does the domain work. This keeps scheduling concerns out of every service. The Dapr Scheduler control plane (etcd-backed) persists jobs and fires them exactly-once cluster-wide.

Version note: the Dapr Jobs API needs daprd ≥ 1.14, so only the scheduler's sidecar + control plane run 1.15.5; the rest of the platform pins 1.12.0.

Job catalogue & scope

Jobs are declared in jobs.yaml (cron 0 0 0 */1 * * or interval @every 90s). State lives in the sclera_scheduler schema (job, job_instance).

ScopeBehaviour
GLOBALFires once per schedule
PER_VDMSFires once per registered VDMS property; vdmsId routes each fire to the right tenant

The trigger / result loop

1
Dapr Scheduler fires a job
POST /job/{name} → sclera-scheduler
2
Scheduler publishes scheduler.trigger
Includes vdmsId for PER_VDMS jobs.
3
Owning service does the work
device-asset / integrations / inspection subscribe to scheduler.trigger.
4
It publishes scheduler.result
SUCCESS / FAILED, with durationMs and any error.
5
Scheduler records the run
ResultSubscriber writes the outcome into job_instance.

Request Flow — Device Add + Audit Log

End-to-End Flow

Pin-to-pin trace

1
Browser POSTs a new device
POST http://localhost:8080/asset/.../adddevice
With header: Authorization: Bearer <JWT>
2
Gateway strips prefix → device-asset
POST http://sclera-cloud-device-asset:8085/.../adddevice
3
DeviceController → DeviceService.addDevice()
JWT validated (multi-tenant, per-issuer JWK). The device is written to PostgreSQL via JPA.
4
Postgres write completes
Device row inserted into device-asset's schema in sclera_assets.
5
UserActionLogService publishes audit events
POST localhost:3500/v1.0/publish/pubsub/device.audit
Also emits device.audit-recorded. The sidecar accepts and writes to Redis immediately.
6
HTTP 200 back to browser
Delivery to subscribers happens asynchronously in the background — the user doesn't wait.
7
Redis → subscriber sidecars
vdms-service AuditSubscriber inserts into user_action_log; sclera-audit consumes device.audit-recorded (deduped).

Timeline — what happens when

t=0ms Browser POST
t=5ms Gateway forwards
t=10ms JWT validated
t=15ms Postgres INSERT done
t=18ms Dapr publish accepted
t=20ms ← HTTP 200 to browser

--- async, after response ---
t=25ms Redis delivery
t=30ms subscribers: audit rows written

Why async for audit?

Speed: the user gets an instant response. Audit logging is a side-effect — no reason to make them wait.
Reliability: Redis + Dapr give at-least-once delivery; the idempotency store makes reprocessing safe.
Eventual consistency: the audit entry appears a few ms after the device is created — query immediately and it may not be there yet.

Database — PostgreSQL with Schema-per-Service

Infrastructure

One instance, isolated schemas

A single PostgreSQL 16 instance (sclera_assets, port 5432) hosts an isolated schema per service. This gives logical DB-per-service separation without operating many database servers.

Migration: the platform moved off MySQL 8 (and a single shared vdms schema) to Postgres 16 with per-service schemas during the Java 21 / Spring Boot 4 upgrade.

Schemas

SchemaOwner
public (default)cloud-device-asset
vdms_svcvdms-service
integrations_svcintegrations
sclera_schedulerscheduler
(inspection schema)inspection

Loose coupling across schemas

Services do not use database-level foreign keys across schemas. Cross-service references are plain scalar ID columns (often UUID strings).

// integrations_svc references a device by ID only — // no FK into the device-asset schema String deviceId; // "dev-123" (UUID)
Why: each service can evolve its tables, run its own Flyway migrations, and (later) be split onto its own database server without untangling cross-schema constraints.
Trade-off: referential integrity across services is the application's job, not the database's — events + idempotency keep things consistent.

Docker Compose — Container Topology

Infrastructure

What runs, and in what order

1
postgres + redis (health-gated)
Start first. Services wait for pg_isready and redis-cli ping before booting.
2
The 12 services
Each built from its own Dockerfile (build context = repo root). JARs compile inside the image — no local JDK/Maven needed.
3
One Dapr sidecar per service
network_mode: "service:<name>" — the sidecar shares the service's network namespace and reaches it on localhost.
4
dapr-scheduler control plane
etcd-backed jobs store on :50006 — only the scheduler's sidecar uses it.
5
Observability + test doubles
otel-collector, jaeger, prometheus, grafana, loki, promtail, httpbin, mailhog.

The network_mode: service:X trick & its gotcha

A sidecar with network_mode: "service:app" shares the exact IP/ports of the service container — so the app reaches Dapr on localhost:3500 with no separate mapping.
Rebuild caveat: rebuilding a service destroys its container, leaving the sidecar pointed at a dead namespace. You must recreate the sidecar too:
docker compose up -d --force-recreate <name>-dapr

Summary

Architecture

4 Dapr building blocks

1
Service Invocation
Sync call by app-id. Caller waits. Used for VDMS lookups.
2
Pub/Sub
Fire-and-forget over Redis. Audit, VDMS changes, scheduler events.
3
State Store
VDMS cache + idempotency keys (Redis).
4
Jobs
Cron control plane fires scheduler.trigger.

5 Key Design Decisions

→
Single gateway, port 8080
No service is exposed directly. All traffic enters through the gateway.
→
JWT auth inside device-asset
Not at the gateway. Multi-tenant: each issuer has its own JWK set.
→
Dapr for all inter-service comms
No hardcoded URLs. Resolve by app-id. Invoke, pub/sub, state, jobs.
→
DB-per-service via schemas
One Postgres, isolated schemas, scalar-ID references — independently deployable.
→
Walking skeletons first
Topology + event contracts staked out before domain logic.

The complete request path

React UI :3000
  ↓ HTTP :8080
API Gateway (route + strip)
  ↓ HTTP :8085
device-asset (JWT + logic)
  ↓ localhost:3500
app-dapr → vdms-dapr → vdms-service
  ↓ Postgres query
  ↑ response back
app-dapr (publish)
  ↓ Redis

subscribers → Postgres

The loop is complete. A device add ends up as a row in Postgres and audit entries in two subscribers — via separate sync and async paths — with the whole journey visible as one trace in Jaeger.
